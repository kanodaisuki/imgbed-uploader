## 2. 方案与取舍

### 2.1 mock 图床：进程内单服务、三 hostname

沿用 `client.test.ts` / `download.test.ts` 的进程内 Node `http` 模式，**一个服务**同时扮演三种角色（`listen(0)` 全接口绑定，随机端口）：

| hostname | 角色 | 依据 |
| --- | --- | --- |
| `localhost:<port>` | 图床 API（`POST /upload`，即 `serverUrl`） | selfHosts |
| `127.0.0.1:<port>/white.png` | 白名单远程图 | 验收 1 |
| `[::1]:<port>/black.png` | 非白名单远程图（待转存） | 验收 1 |

hostname 敏感逻辑（selfHosts 自识别 / remoteWhitelist 精确等值）要求三个 URL 的 hostname 互不相同且前两者不等于 `serverUrl` 的 host——环回地址恰好有三个名字（`localhost` / `127.0.0.1` / `[::1]`），一台服务全包。远程图返回 `TEST_PNG` 字节（常量内联在 `mockImgbed.ts`，不从 `out/client` 跨树 import——§2.3 的双树问题）。`URL.hostname` 对 IPv6 **保留方括号**（实测 `'[::1]'`）；自识别/白名单按 hostname 等值比较（`flow.ts`），故任何把 `[::1]` 当白名单条目的组合必须带括号。转存下载的「非图片嗅探」仍走真实字节路径。

- 路由约定：`POST /upload` 从 multipart body 嗅 `filename="…"`，按**文件名编程响应**（行为队列：200 成功 / 400 `UPLOAD_FORMAT_NOT_ALLOWED` / 401 / 403 / 延迟），默认 200 返回 `{ src: '/file/<该次上传的文件名>', publicUrl: '…' }`；`GET /*.png` 按 path 返回图片字节或 403（默认 200，用例可 `setGetStatus` 改）。
- `src` **由上传文件名派生**：4.3 首级 `customCdn + 文件ID`（`extractFileId` 取 `src` 的 pathname 剥 `/file/`）的期望值全部建立在这条上；`testConnection` 的行为队列键因此固定为 `imgbed-test.png`（`client.ts` 的 `TEST_FILE_NAME`）。
- 请求日志：计数、文件名、query、headers（断言「图床不新增文件」零/不增请求、转存请求不带凭据头——T10 口径）。
- 生命周期：`stop()` **先 `server.closeAllConnections()` 再 `close()`**——undici 的 keep-alive 空闲连接会让裸 `close()` 永远等不到 callback，teardown 挂死。`reset()` 清 requests / 计数 / 行为队列，每用例 beforeEach 调（否则验收 4 的「计数不变」跨用例串味）。
- ❌ 被否：独立 mock 进程——多一层进程管理，无必要；三台 HTTP 服务——一台多 hostname 即可，端口只有一个。

### 2.2 观测面：打桩通知 + 打桩 Output Channel

断言粒度要到「明细行」（验收 8 服务端错误原文、验收 2 失败原因、验收 13 提示语），而明细只进 Output Channel：

- 打桩 `vscode.window.showInformationMessage / showWarningMessage / showErrorMessage`：记录 `{id, kind, message, buttons}`，返回**可控 Promise**（默认 resolve `undefined` 防悬挂——`runTestConnection`（`await showErrorMessage`）与 `ensureReady`（`await showWarningMessage`）都不打桩就永不返回、测试挂死）。`click(id | 摘要子串, '重试失败项')` 以指定按钮 resolve**指定**通知来驱动回调；**不许按「最近一次未决通知」定位**——成功路径的通知永不 resolve、会跨用例累积，重试用例会点到上一个 suite 的对象。
- 打桩 `showInputBox` / `showOpenDialog`（默认均 resolve `undefined`）：按钮「重新设置认证信息」一旦被点到就走 `promptCredential`、`uploadFile` 无参入口走选择框——真 UI 是模态的，会抢焦点污染后续用例；命令面板入口用例反过来用 `showOpenDialog` 返回指定 Uri 列表。
- 打桩 `vscode.window.createOutputChannel`：返回**整个测试文件共用的一个**假 channel（记录 `appendLine`），`lines.length = 0` 在 beforeEach 清空。`ui.ts` 的 `channel ??=` 是模块级缓存——还原后重新 stub 只会造出第二个空数组，扩展仍写第一个，明细断言静默落空。生效边界是**首个 `showReport`**（`channel ??=` 懒创建，与 activate 无关），§2.4 整文件启用即覆盖；install/restore 挂 suiteSetup/suiteTeardown 运行期钩子，**不放模块顶层**——mocha 先加载全部文件再执行，顶层 install 会串到其它单测文件。
- 通知 `kind` 是可断言的观测点：`showReport` 失败数 >0 走 warning、否则 info（`ui.ts`），验收 1 与验收 2 的形态差别就在这。
- 测试与扩展包虽是两棵模块树（§2.3），但共享 `vscode` 模块单例，打桩对扩展包内代码同样生效。
- ❌ 被否：只断言通知摘要——摘要只有计数，验收 8「原样呈现」断不到；读 OutputChannel 文本——无读取 API。

### 2.3 凭据注入：`extension.ts` 导出测试钩子（唯一生产码变更）

扩展从 `dist/extension.js`（esbuild 包）加载、测试从 `out/`（tsc）加载，**模块树不同源**——`client.test.ts` 的 `initSecrets` 打桩对走真实命令的集成测试无效；SecretStorage 只能经 `ExtensionContext` 取。故 `activate()` 返回 `{ setCredential, clearCredential }`（re-export 自 `secrets.ts`，约 3 行），测试经 `vscode.extensions.getExtension('kanodaisuki.imgbed-uploader').activate<ExtensionApi>()` 拿钩子种/清凭据（`@types/vscode` 的 `activate` 是泛型，测试侧收窄即可，不新增类型文件）。

- ❌ 被否：打桩 `showInputBox` 走 `setCredentials` 命令——T1 设计空输入不清理凭据，「未配置凭据」场景（验收 6）无法清场，且 SecretStorage 在 `.vscode-test` 跨次运行残留，用例顺序敏感。

### 2.4 配置、fixture 与隔离

- 配置注入：suiteSetup 起 mock 后 `getConfiguration('imgbedUploader').update(key, value, ConfigurationTarget.Global)`；**改前先快照** `inspect()?.globalValue`，teardown 按快照还原（不是一律 `undefined`——test-cli 的 user-data-dir 被复用时不能写坏开发机全局设置）。`authType` 用默认 `authCode`（6 的引导场景靠它触发）。
- 凭据：suiteSetup **先 `setCredential('integration-test')`**——`authType=authCode` 下 `ensureReady` 无凭据会拦掉所有用例；唯一例外是验收 6②（`clearCredential()` 后跑）。suiteTeardown 再清一次。
- fixture：`os.tmpdir()` 下建临时目录，写 `mockImgbed` 导出的 `TEST_PNG` 字节到 `img/a.png`、`img/my pic.png` 等 + md 文档，`openTextDocument(fsPath)` + `showTextDocument`；untitled 用 `openTextDocument({ content, language: 'markdown' })`（验收 13）。
- 隔离：每用例独立文档；teardown `closeAllEditors` + 删临时目录。打桩**整个集成文件期间启用**（假 channel 是单例，§2.2），文件末尾 `restore()`；mocha 按文件顺序执行，不污染同进程其它单测文件。
- 等待策略：命令本体 `await executeCommand` 即完成；「重试失败项」回调经 `showReport` fire-and-forget，断言用 `waitUntil`（轮询 mock 计数 / 文本，10s 上限——慢机与杀软扫描下 5s 偏紧）。undo 后同样用 `waitUntil` 等模型落地。

## 5. 测试方式

本任务即测试。开工顺序：先用最小用例实测打桩可写性（§6 第 1 条），再铺矩阵——不可写要换方案，先焊死接口会白做。验收：`pnpm test` 全绿 = 既有全部单测 + 新增 14 个集成 suite；连续跑两遍验证无状态残留（凭据 / 配置清场 + mock reset 有效性）。改动面自检：`pnpm run compile`（check-types + lint）通过。

## 6. 边界说明

- **打桩可写性**：依赖 `vscode.window` 属性可写，实施第一步先用 5 行用例实测。不可写时退路按成本排序：① `Module._load` 拦 `require('vscode')`，返回带假 `window` 的代理对象（**零生产码**，在 `activate()` 前装好即可，因为扩展是懒加载的）；② 把通知出口挂到 `extension.ts` 钩子（生产码多几行，接口不变，§3 的 `ExtensionApi` 需扩容）。
- **`[::1]` 与 Windows**：win32 开发机默认可用，但 `listen(0)` 全接口绑定可能弹防火墙；被拒时退路 = `127.0.0.1` + `[::1]` 各起一个 listener（共用同一 handler，改动比“对调角色”小）。若走“对调角色”退路，记住 `URL.hostname` 含方括号（`'[::1]'`），白名单条目必须写 `[::1]` 才会命中。
- **SecretStorage 与用户设置**跨次运行持久化：清场逻辑（凭据钩子 + 配置快照还原）是用例可重复的前提，以「连跑两遍」验证；suiteTeardown 也要清凭据，避免污染开发机。
- **`resolveUrl` 的裸空格**（验收 9）：`extractFileId` 解码 pathname 后直接拼 `customCdn`，URL 值含空格（`http://…/cdn/my pic.png`）；markdown 上下文由 `markdownText` 包 `<>` 后是有效链接，但 URL 值本身带空格（复制进 HTML 属性等场景需编码，`htmlText` 已处理）。本任务**按现状钉住**该字符串并在报告里注明；是否在 `resolveUrl` 改百分号编码属业务码变更，由 T11 缺陷修复阶段单独裁决（改则同步改用例期望）。
- **超时与上传锁**：集成用例与既有单测同进程顺序执行，stub 仅本文件 install/restore。若某用例超时被 mocha 中止，命令仍在后台跑、`ui.ts` 的 `uploading` 锁要等命令返回才释放——后续 suite 会看到「上传进行中」。出现超时的处置是重跑整个测试文件，别指望后续用例自愈。
