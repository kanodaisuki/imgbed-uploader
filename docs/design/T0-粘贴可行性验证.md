# T0 方案设计：粘贴可行性验证（spike）

- 状态：草稿（待评审）
- 对应任务：[`../plans/PLAN.md`](../plans/PLAN.md) T0（0.5d，timebox）
- 前置：无；产出作为 T9（粘贴上传）方案设计的输入

## 1. 背景与验证目标

FR-3 要求"粘贴图片时自动上传并插入链接，失败时不丢图"。VS Code 没有公开的粘贴事件，接管粘贴的技术路线存在不确定性，是全插件最高风险点。T0 不写正式代码，只验证技术路线并做出选型决策。

验证目标一句话：**能否可靠地拦截"图片剪贴板数据 → Markdown 编辑器"的粘贴，异步上传后插入链接，并在失败时回落到 VS Code 默认粘贴行为。**

## 2. 候选方案与取舍

### 方案 A：`DocumentPasteEditProvider`（首选）

`vscode.languages.registerDocumentPasteEditProvider(selector, provider, { pasteMimeTypes: ['image/*'] })`，provider 的 `provideDocumentPasteEdits` 中取 `dataTransfer` 图片字节 → 上传 → 返回插入 `![](url)` 的 edit。该 API 已于 ~VS Code 1.97（2025 初）转正（stable）；现行签名：`provideDocumentPasteEdits(document, ranges, dataTransfer, context, token)` 返回 `DocumentPasteEdit[]`，长任务可选 `resolveDocumentPasteEdit` 两段式。

- ✅ VS Code 原生粘贴管线，Ctrl+V / 右键粘贴 / 菜单栏 Paste 全部覆盖
- ✅ provider 不返回 edit 时自动回落默认粘贴行为 → 满足"失败不丢图"的前提（注意：验收 11 的"落盘 + 本地链接"兜底实际由内置 markdown 扩展提供，见 V4）
- ✅ 不改用户键位
- ⚠️ 内置 `markdown-language-features` 扩展同样注册了图片 paste provider（双方都响应 `image/*`），需验证 `yieldTo`/`kind` 能控制默认 edit 与粘贴选择 widget（V6b）

### 方案 B：覆盖内置命令 `editor.action.clipboardPasteAction`

`commands.registerCommand` 用同 ID 覆盖内置粘贴命令。**被否**：覆盖内置命令非官方支持行为，VS Code 升级随时失效，且其他扩展同抢会出诡异问题。

### 方案 C：`keybindings` 重绑 Ctrl+V（A 的降级备选）

`contributes.keybindings` 把 `Ctrl+V` 在 `editorLangId == markdown || editorLangId == mdx` 时绑到自定义命令。

- ✅ 无粘贴 API 依赖，VS Code 升级不易失效
- ❌ 覆盖不了右键菜单/菜单栏的"粘贴"入口；与用户自定义键位冲突；可发现性差
- ❌ 稳定 API 无图片剪贴板读取能力（`env.clipboard.readText` 仅文本），拿字节须走系统命令（PowerShell/pbpaste/xclip）或 native module，自带跨平台风险——C 并非"零风险"，只是风险形态不同

### 方案 D：不接管粘贴，提供命令「粘贴并上传」

**兜底**：仅当 A/C 均不可行时采用，体验打折（违反 FR-3 自动性），需回需求变更。

## 3. 验证点清单（spike 手工逐条过，按决策价值排序：V1 → V2/V2b → V4 → 其余）

| # | 验证点 | 通过标准 |
| --- | --- | --- |
| V1 | API 可用性 | `registerDocumentPasteEditProvider` 可直接注册，无需 `enabledApiProposals`（已转正，预计 15min 确认签名即可）；若引擎 `^1.146` 实测仍需 proposal → 记录发布阻塞风险，直接转方案 C |
| V2 | 图片数据到达 | 截图后 Ctrl+V，provider 被调用，`dataTransfer` 中 `image/png`（及 jpeg/gif/webp）条目能取到完整字节（注意可能是 file 型 item，走 `file()`） |
| V2b | 文件粘贴数据 | 复制图片文件（资源管理器）后粘贴：DataTransfer 中是 `text/uri-list`/文件项还是 `image/*`，`pasteMimeTypes: ['image/*']` 是否被调用（FR-3 含"复制的图片文件"用例） |
| V3 | 异步耗时 | `provideDocumentPasteEdits` 内模拟 3–8s 网络上传：粘贴管线会等待、上传期间无编辑器卡死。**API 无超时概念**：provider 挂起 = 粘贴挂起，超时须 spike 自实现（upload 加超时，超时返回 undefined 回落默认粘贴）；`token` 取消后回落默认粘贴、无报错、无残留编辑。**记录上传等待期间的视觉反馈**（光标 spinner / 无任何反馈）：若无反馈，T9 需自实现 pending 提示 |
| V4 | 降级不丢图 | provider 返回 undefined / 抛错 时默认粘贴照常执行，**markdown 与 mdx 分别验证**。注意兜底并非 VS Code 核心提供：markdown 下"图片落盘 + 插入本地链接"来自内置 markdown 扩展的 paste provider（受 `markdown.editor.filePaste.enabled` 控制，用户可关）；mdx 下该降级可能不存在，若图片直接消失 → 记录为 T9 需自实现落盘降级的风险。**回落发生时插件需提示失败原因**（FR-3 要求）：验证 provider 返回 undefined 前弹提示不影响回落流程 |
| V5 | 开关行为 | 固定"始终注册、`pasteUpload=false` 时返回 undefined"（避免配置切换时 re-register）：默认粘贴正常 |
| V6 | 入口覆盖 | Ctrl+V、编辑器右键"粘贴"、菜单栏"编辑→粘贴"均走 provider；连续快速粘贴多张正常（记录并行/串行语义） |
| V6b | 与内置 provider 共存 | 内置 markdown 图片 paste provider 同在时，默认应用的 edit 归属、粘贴选择 widget 是否弹出；`yieldTo`/`kind` 能否让本插件 edit 成为默认 |
| V7 | 语言范围 | selector 命中 `markdown` 与 `mdx`（后者需装 MDX 扩展验证） |
| V8 | 选区语义 | 有选区时粘贴替换选区，与默认行为一致 |
| V9 | 光标与撤销 | 插入后光标落在链接之后（FR-3）；Ctrl+Z 一次撤销粘贴插入的内容，文档复原（4.7 对粘贴路径同样成立） |

## 4. 判定标准（决策规则）

- **V1、V2、V4 全过** → 采用方案 A，T9 按 A 出设计
- **V1 或 V4 不过** → 转方案 C，T9 按 C 出设计（风险表同步更新；C 需自备图片剪贴板读取手段，见 2 节）
- **V2 不过（拿不到图片字节）** → A/C 均受阻，升级为风险项并回 T9 重新设计（可能需要读剪贴板的替代手段）
- **V3 不过（阻塞不可接受或取消行为不可控）** → A 仍可用但需异步占位模式，或转 C；回 T9 评估
- **V6b 不过（抢不过内置 provider）** → T9 设计必须包含 `yieldTo`/`kind` 优先级控制，列入风险表；**极端分支**：优先级控制也无效（默认 edit 始终归内置 provider，弹出粘贴选择 widget）→ 评估"widget 二选一"的可接受性，不可接受则转方案 C
- **V2b 不过（文件粘贴不触发 provider）** → 记录 FR-3"复制的图片文件"用例缺口，回需求确认取舍（或 T9 补 `text/uri-list` 处理）
- **V4 的 mdx 降级不成立** → 记录风险：验收 11 在 mdx 下需 T9 自实现落盘降级
- timebox 0.5d 到期未决 → 默认按方案 C 推进，不阻塞 T1–T8（仅 T9 依赖本结论）

## 5. 对既有模块的影响

- spike 代码独立于正式代码：放 `spike/` 临时目录（不打包、不提交 `src/`），或独立分支，结论后删除。
- 若 A 通过，`paste.ts` 预期接口：`registerPasteProvider(cfg: Config, upload: UploadFn)`；上传复用 `client.ts` 的 `upload()`（内存字节入参，4.2 约定），失败降级由 VS Code 管线兜底，无需自实现。**spike 只验证单段式**（上传在 `provideDocumentPasteEdits` 内、失败返回 undefined）；`resolveDocumentPasteEdit` 两段式优化留给 T9，其失败回落行为未验证。
- `package.json`：仅在 API 为 proposed 时需要 `enabledApiProposals`——这将成为发布阻塞，V1 必须给出明确结论（已转正，预计不适用）。

## 6. 测试方式

- 手工验证（真实剪贴板 + 真实按键，自动化不可靠）：第 3 节各条逐条记录结果，附 VS Code 版本与必要截图。
- spike 上传目标**优先本地 mock HTTP 服务**（确定性、可模拟慢响应/失败），公开测试端点仅作备选；仅验证管线等待行为，不验证上传语义。
