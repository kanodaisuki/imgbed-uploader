- 状态：已冻结（2026-11-19 评审通过并实现；自动化测试 27 项 + 真实图床人工走查全部通过，T3 验收通过）
- 对应任务：[`../plans/PLAN.md`](../plans/PLAN.md) T3（0.5d）
- 前置：T2（`client.ts` 上传原语）。验收映射：验收 6（凭据错误时给出明确失败原因）
- 里程碑：本任务结束 = v0.1（可手动上传验证链路，PLAN §3）

## 1. 范围

实现「测试连接」命令（需求第 6 节）：`testConnection(cfg)` 上传一张 1x1 测试 PNG 做**端到端**验证（地址 + 凭据 + 渠道一次覆盖），成功时提示测试文件 URL（用户自行忽略或删除，插件无删除权限）；命令层给出成功/失败通知与可行动作。不含任何文档编辑行为，是 T2 上传原语的第一个业务消费方。

## 2. 方案与取舍

### 2.1 验证方式：真上传测试 PNG（需求第 6 节已定），不做轻量预检

需求已冻结实现约定「上传一张 1x1 测试 PNG 验证端到端」。端到端的含义：`serverUrl` 可达 + 鉴权通过 + 所配渠道可用 + `responseFormat=object` 响应可解析，一次请求覆盖四层，测试结论与真实上传完全一致。

- ❌ 被否：先 `HEAD/GET {serverUrl}` 做可达性预检——只验证地址，鉴权/渠道/响应格式全漏；图床也未必暴露免鉴权的根路由，预检结论不可靠
- ❌ 被否：调用管理类 API（文件列表 / Token 校验）做只读验证——管理 API 是非目标（需求 1.3），且 `apiToken` 只要求 `upload` 权限，调管理接口反而会 403 误报

### 2.2 测试图数据：内置 base64 常量

`client.ts` 内置 1x1 PNG 的 base64 常量（约 70 字节），用 `Buffer.from(b64, 'base64')` 解码为 `Uint8Array`（扩展宿主 Node 20，与 T2 同栈）。零资源文件、零生成逻辑，esbuild 单文件打包无额外处理。

- ❌ 被否：打包 `test.png` 资源文件运行时读取——`dist/extension.js` 单文件打包后资源路径解析易碎
- ❌ 被否：程序化构造 PNG（IHDR/IDAT/CRC 样板）——百余字节易错样板，纯负担

请求文件名固定 `imgbed-test.png`（经 T2 的 MIME 映射得 `image/png`）。注意**落库名由服务端 `uploadNameType` 决定**（`default` 加前缀、`index`/`short` 完全改名），「图床文件列表中一眼可辨、易找易删」仅在 `default`/`origin` 命名下成立（已知限制，见 §6）。❌ 被否：时间戳命名（`imgbed-test-20261119-*.png`）——每次测试留一个难清理的文件。

### 2.3 `testConnection`：薄封装复用 `upload()`，不自行拼请求

`testConnection(cfg)` = `upload({ name: 'imgbed-test.png', data: TEST_PNG }, cfg)`，catch `UploadError` 转成 `{ ok: false, detail, status?, code? }`；**其余异常也 catch-all 转** `{ ok: false, detail: '测试连接失败：<message>' }`（非 `Error` 抛出物以 `String(err)` 取文本），不冒泡成 VS Code 英文通用报错（需求 2 文案口径）。参数映射、鉴权、URL 优先级（4.3）、错误映射（4.9）、超时全部复用 T2，零重复逻辑、无漂移风险。

- ❌ 被否：`testConnection` 自行拼 `fetch` 请求——与 T2 的映射/鉴权/错误处理重复两份，日后改口径必漂移；且"测试通过但真上传失败"的歧义正是要避免的

成功时 `url` 即 `upload()` 按 4.3 优先级解析的结果（`customCdn + 文件ID` → `publicUrl` → `serverUrl + src`），与真实回写链接同源。

### 2.4 提示与可行动作（验收 6）

通知由 `commands.ts` handler 直接弹（单命令场景，不进 `ui.ts`；批量汇总报告机制归 T6）：

- **成功**：`showInformationMessage(detail)`，detail 为「连接成功（渠道：<uploadChannel>），测试文件已上传：<url>（可在图床中自行删除）」——带渠道名把「端到端含渠道」（§2.1）的语义显性化，也便于发现配错渠道；附「复制链接」按钮（`vscode.env.clipboard.writeText(url)` 后 `vscode.window.setStatusBarMessage('测试文件链接已复制', 3000)` 轻反馈——按钮点击后通知即消失，无反馈像没反应）。不提供删除入口（管理 API 非目标）。
- **失败**：`showErrorMessage(detail, ...)`，detail 即 `UploadError.message`（服务端原文透传 + 401/403 追加「请检查认证信息」，验收 8 口径）。按钮规则：**固定附「重新测试」**（`executeCommand('imgbed-uploader.testConnection')` 重跑本命令——网络抖动、改完凭据/设置后重测是最高频下一步），另按情形附一个针对性按钮：

| 情形 | 判定依据 | 第二按钮 |
| --- | --- | --- |
| 认证失败（`authType != 'none'`） | `status` 401/403 | 「重新设置认证信息」→ `executeCommand('imgbed-uploader.setCredentials')` |
| 认证失败（`authType == 'none'`） | `status` 401/403 | 「打开设置」→ `workbench.action.openSettings` 搜 `imgbedUploader.authType`；detail 后追加「当前 authType=none，若服务端需要认证请改用 authCode/apiToken」（handler 拼接，`testConnection` 的 detail 维持与真实上传同源，见 §6） |
| 地址无效 | `code === 'INVALID_SERVER_URL'`（T2 入口预校验抛错携带，勘误见 T2 §7） | 「打开设置」→ `workbench.action.openSettings` 搜 `imgbedUploader.serverUrl` |
| 其他（网络不通 / 超时 / 服务端拒绝） | 兜底 | 无第二按钮，detail 本身已可行动 |

**`authType=none` 分流的原因**：`none` 时凭据永远不会随请求发送（T2 `buildQuery`/`headers` 均不带），只引导「重新设置认证信息」是死胡同——用户录完凭据再测仍 401。判定需要错误侧的 `status`/`code` 与 `cfg.authType`，故 `TestResult` 非 ok 时透传 `status?`/`code?`（对 PLAN §2 草案的微调，见 §3；`code` 由 T2 勘误补充，`UploadError` 本就带 `code` 字段）。全部分支均为**结构化判定**，不匹配任何文案文本。❌ 被否：失败通知固定附「重新设置认证信息」「打开设置」两按钮——多数失败与凭据/地址无关，按钮噪音（「重新测试」永远相关，故固定附）；❌ 被否：靠 message 文本猜错误类型——脆弱。

### 2.5 进度提示

handler 直接调 `vscode.window.withProgress({ location: Notification, title: '正在测试连接…', cancellable: false })` 包裹调用（**不经 `ui.ts` 封装**——PLAN §1 划归 `ui.ts` 的 withProgress 指 T6 批量进度封装，单命令场景直接用 vscode API）：请求最长 60s（4.2 固定值），无反馈会像卡死。

- ❌ 被否：可取消——需向 `upload()` 传 `AbortController`（T2 接口未提供，opts 明确仅测试注入用），单次测试收益低
- ❌ 被否：不给进度——60s 静默体验不可接受

## 3. 接口

```ts
// client.ts（新增，PLAN §2 草案的落实）
// 可辨识联合：ok 为真时必有 url，为假时才可能有 status/code
export type TestResult =
  | { ok: true; detail: string; url: string }       // url：测试文件 URL（4.3 优先级）
  | { ok: false; detail: string; status?: number; code?: string }; // status/code：供命令层结构化选可行动作（§2.4）
// detail 两种分支都有：给用户看的完整文案（简体中文，需求 2）

export const TEST_PNG: Uint8Array;                    // 1x1 PNG，base64 常量解码
export async function testConnection(cfg: Config): Promise<TestResult>;
```

较 PLAN §2 草案 `Promise<{ ok: boolean; detail: string; url?: string }>` 有两处微调（§2.4 的按钮分流需要）：改**可辨识联合**、失败侧增加可选 `status?`/`code?`，其余字段口径不变；PLAN §2 明确为草案，正文不回改，勘误登记于 PLAN「变更记录」。

命令 handler（`commands.ts`，替换桩）：`ensureReady(vscode.window.activeTextEditor?.document.uri)` → `withProgress(testConnection(cfg))` → 按 §2.4 弹通知（成功附「复制链接」；失败附「重新测试」+ 情形按钮）。`ensureReady` 复用 T1 引导（4.10），**未配置时直接弹引导、不发请求**。testConnection 无编辑器入口，活动文档 URI **可为 undefined**（如只开着设置页）：回落工作区级配置继续，**不要求先打开文档**（取 URI 方式与 T1 桩命令一致，见 `src/commands.ts`）。

## 5. 测试方式

沿用 T2 的模式：vscode-test 内普通 mocha + 进程内 mock 图床（Node `http`，随机端口，见 `src/test/client.test.ts`）。

- **单测**：`TEST_PNG` 解码后断言 PNG 签名魔数 + IHDR 宽高为 1x1（防常量损坏/截断）。仅此一处为测试导出 `TEST_PNG`；更关键的链路字节验证放集成侧（见下条 mock 断言）。
- **集成**（mock 图床，复用 `src/test/client.test.ts` 的进程内 mock）：
  - 200 + `{src}` → `ok`、`url` 按 4.3 解析、`detail` 含渠道名与 URL；mock 侧断言收到的 multipart 文件名为 `imgbed-test.png`、字段名为 `file`、**文件字节为合法 PNG**（签名魔数 + IHDR 1x1，验证真实链路字节而非仅常量）；
  - 401 + `{"error":"Invalid auth code"}` → `ok=false`、`detail` 含服务端原文 + 「请检查认证信息」、`status=401`（验收 6 的自动化部分）；
  - 400 `UPLOAD_FORMAT_NOT_ALLOWED` → `detail` 为服务端原文（复用 T2 已测的错误透传路径，抽 1 条即可）；
  - 连接被拒（指向未监听端口）→ `ok=false`、`detail` 为「上传失败：…」（「上传」字样有意保留，见 §6）；
  - `serverUrl` 非法 → `detail` 为「图床地址无效，请检查 serverUrl 配置」、`code='INVALID_SERVER_URL'`（§2.4 结构化判定的落点）；
  - **`serverUrl` 已指向 mock、凭据缺失**（`authType=apiToken`）→ `testConnection` 不被调用、**mock 侧计数为零请求**（4.10 引导前置拦截，自动化断言替代人工观察；`serverUrl` 未配置时没有 mock 可计数，零请求是平凡真，不作断言场景）。
- **手动走查**（真实 CloudFlare ImgBed 实例——T2 §5 明确留给本任务的覆盖项）：
  - 正确凭据执行「测试连接」→ 成功通知含测试文件 URL，浏览器打开显示 1x1 图；
  - 凭据改为错误值 → 失败通知给出明确原因（服务端原文），「重新设置认证信息」按钮可用；
  - 未配置 `serverUrl` / 凭据 → 弹引导即中止（零请求已由自动化断言覆盖，原「网络面板」写法不可执行——扩展宿主 fetch 不进渲染进程 Network 面板）；
  - 主观体验：进度通知不刷屏、60s 内有反馈。

## 6. 边界说明

- 测试会在图床留下一个真实文件；插件无删除权限（管理 API 非目标，需求 1.3），文案提示用户自行删除或忽略。
- **本地不判定凭据对错**：`ensureReady` 只检查存在性，对错由服务端裁决（验收 6 的失败原因即服务端 401/403 原文透传）。
- 测试上传携带当前全部上传设置（渠道、目录、命名、有效期等）：测试即真上传，所测即所得；`expire` 开启时测试文件同样带有效期，可接受。
- 超时固定 60s 不为测试单独缩短（4.2 固定值口径；T2 的 `opts.timeoutMs` 仅测试注入用，不在业务代码出现）。
- `authType=none` 时无需凭据，`ensureReady` 不拦；`authType=authCode/apiToken` 但凭据为空由 `ensureReady` 前置拦截（4.10）。
- 成功提示的 URL 按 4.3 优先级解析：`customCdn` 配置时提示的是 CDN 链接；CDN 回源是否生效**不在**本命令验证范围（无读取/删除 API 可断言，v1 不做）。
- **落库文件名由服务端 `uploadNameType` 决定**：请求文件名恒为 `imgbed-test.png`，但 `default` 加前缀、`index`/`short` 完全改名，重复测试服务端还可能去重改名——「易找易删」不保证成立（§2.2），属已知限制，不做本地规避。
- **失败文案有意与真实上传同源**：测试连接语境下会出现「上传超时（60 秒）」「上传失败：…」等含「上传」字样的文案（T2 `upload()` 口径）。保持同源防止两套口径漂移，**不为测试连接改写文案**；`authType=none` 的引导提示（§2.4）由 handler 在 detail 外拼接，不污染 `testConnection` 的 detail。
- `code` 字段混装服务端值（如 `UPLOAD_FORMAT_NOT_ALLOWED`）与本地值（`INVALID_SERVER_URL`）：本地生成的 code 一律用 `INVALID_*` 前缀区分，服务端 code 原样透传不改写。
- 并发、重试、批量语义不涉及（T6）；本命令与上传命令不互斥（单发无状态，T2 已保证可并发调用）。
